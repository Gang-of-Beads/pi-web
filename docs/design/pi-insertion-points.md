# pi's insertion points in PI WEB

Status: audit and plan, 2026-10-09. Owner, 2026-10-09: "PI WEB is generic and adapts to no particular plugin. Plugins have their scenarios; PI WEB provides a set of generic insertion points, the same philosophy as pi. pi already implements many insertion points; PI WEB's insertion points are a superset of pi's, including web UI ones that give users more on the web."

## The rule

1. **Every pi insertion point works in PI WEB without a PI WEB plugin.** An extension written for pi's terminal shows in PI WEB as it does there. Where pi draws a TUI component, the daemon renders that same component to lines (`customScreenHarness`, `renderCustomScreen`, as `ctx.ui.custom` and `setWidget` already do) and the page shows the lines.
2. **PI WEB adds web insertion points on top.** A PI WEB plugin may draw the same thing natively (message renderers, panels, pages, composer contributions). When a plugin claims something, its drawing wins over the extension's terminal drawing.
3. **Core never names an extension.** What an extension's records mean, and how its cards behave, is the extension's and its plugin's business, decided by what the extension does in pi. Only PI WEB's own product behaviour is the owner's question.

So every drawn thing resolves in one order: a PI WEB plugin's web renderer, else the extension's own pi renderer drawn to lines, else pi's default.

## Audit against the pi 1.0.4 SDK (`core/extensions/types.d.ts`)

### Things that run inside pi

`registerTool`, `registerCommand`, `registerProvider`/`unregisterProvider`, `registerVirtualModel`, `registerMcpServer`, `on(event)`, `sendMessage`, `sendUserMessage`, `appendEntry`, `exec`, `setModel`, `setThinkingLevel`, `setActiveTools`, `setSessionName`, `setLabel`, the getters, `events`: pi runs them in the session daemon exactly as in its terminal. Commands appear in the slash list (`sessionCommandService.ts`); labels in the session tree (`sessionTreeProjection.ts`). **Supported.**

`registerFlag`/`getFlag`: CLI flags; the daemon starts pi with none, so `getFlag` answers the default. **Not applicable until PI WEB has a place to set flags** (a config key would be the way; no extension needs it yet).

## Slices

Each slice: state-diagram entries for new rows or frames in the same commit, a bob review, and 8505 live checks with a real extension that uses the insertion point, old build against new.

1. **Message and entry renderers.** Built 2026-10-09. Known limit: a session read without its runtime (D5: reading a closed session never opens it) has no renderers, so rows read then show the default until the page reads the session again after it runs; drawing at `entry_appended` time and keeping the lines would lift it, if it matters in use. The daemon's projection asks the session's extension runner (`getMessageRenderer`, `getEntryRenderer`) and, when one exists, renders the component at the transcript width and ships the lines with the row (`drawn: string[]`, collapsed as pi first shows them; the expanded drawing joins slice 7), re-rendered when the transcript is read, never stored in the session file. A `custom` entry is projected only when an extension registered a renderer for its type, as in pi. The page draws, in order: a plugin's renderer for the tag, the drawn lines, the content as markdown, and only then "Nothing on this machine renders <tag>". The plugin API's message renderers also receive entry rows (`kind: "message" | "entry"`), so a plugin can draw either natively.
2. **Tool renderers.** Built 2026-10-09. The same lines for a tool call's arguments and result, in the generic tool card, when an extension draws the tool: `resolveToolRenderers` over the extension tool's own `renderCall`/`renderResult` (a built-in tool is not an extension tool, so only a resolver draws it). Live frames carry them, and the daemon keeps a call's arguments from its start to its end because pi's end event does not repeat them. Not carried over: `renderShell: "self"` (PI WEB keeps its card chrome), renderer `state` shared between a row's call and result (each drawing starts fresh), and `invalidate` (a renderer cannot ask for a redraw).
3. **Markdown transformers.** Built 2026-10-09. pi passes user, assistant and thinking markdown through each extension's `registerMarkdownTransformer` before drawing it (`markdown-transform.js`: in load order, a transformer that throws or answers a non-string is skipped), with `{ messageType, isStreaming, availableWidth }`. PI WEB draws markdown in the browser, so:
   - The daemon applies the session's transformers to each finished text: a user message's text, an assistant message's text parts, and its thinking (`messageType` as pi names it, `isStreaming: false`, `availableWidth` the transcript drawing width, 56). The part keeps its own text and gains `displayText` when a transformer changed it.
   - History pages carry it for an open runtime; a live `message.end` carries it, so the reply in progress shows its raw text while it streams and the transformed text once it ends. pi transforms while streaming too, on the whole text at each redraw; the page only has deltas until the end, which is the one difference, and it lasts until the reply ends.
   - The page draws `displayText` when present. Copy, quote, the composer's history and every other use of a message's text keep its own text: the transformation is how it is drawn, not what was said.
   - A session read without its runtime has no transformers, as for slices 1 and 2.
4. **Shortcuts as actions.** Built 2026-10-09. pi binds each `registerShortcut(key, { description, handler })` in its editor (`getShortcuts` skips one that a reserved built-in key owns and reports the conflict), runs `handler(createContext())` on the key, and lists the shortcuts under "Extensions" in its hotkeys help. In PI WEB:
   - The daemon puts the session's shortcuts in its status (`extensionShortcuts: [{ key, description, extension }]`, from `runner.getShortcuts`), and runs one on `POST /sessions/:id/extension-shortcuts/run { key }` with `handler(runner.createContext())`, the same context pi's runner gives commands, so `ctx.ui` dialogs, notices and the composer work as they do for commands. The run answers at once, since a handler may open a dialog; a handler that throws or rejects says "Shortcut handler error: …" as an error notice on the session, as pi shows it.
   - The page turns each into an action of the selected session in the Actions palette ("<description>", the extension named beneath by its `piWeb.title` or package name, as its Go to page is), and binds its key through PI WEB's own shortcut engine (`resolveShortcutBindings`), so a key PI WEB already uses keeps PI WEB's action and the extension's action stays in the palette without that key, as pi keeps its reserved keys, and Settings → Shortcuts can rebind it like any action. pi's key names (`ctrl+shift+x`) map to PI WEB's shortcut notation; a key PI WEB does not bind is listed without one: without Ctrl, Cmd or Alt (typing would trigger it), or with Ctrl or Cmd alone (the browser's: reload, close, new tab, find, save; a terminal hands pi `ctrl+r`, a browser keeps it).
   - The actions follow the selected session: another session's shortcuts are never offered, and a session read without its runtime offers none until it runs.
5. **Footer and header on the widget page.** Built 2026-10-09. pi has one footer and one header: `setFooter(factory)` and `setHeader(factory)` replace its own, the last extension to call replacing the one before, and `undefined` restores pi's. PI WEB's footer and header are its own, so, as for `setWidget`:
   - The daemon builds the component with the same harness as a widget and draws it the same way (when it asks, or once its drawing is a second old, bounded like a widget), under the extension that called, and the status carries it as a widget with placement `header` or `footer`.
   - The extension's Go to page shows it with its widgets, the header first and the footer last. Clearing it leaves the page saying the extension shows nothing now, as a cleared widget does.
   - A footer factory gets pi's `footerData`: the git branch as pi reads it (null outside a repository, `detached` on a detached HEAD; pi's `FooterDataProvider` is not exported, so its reading is mirrored), the extensions' statuses, and how many providers have models. The branch is read at each drawing instead of watched, so `onBranchChange` reports nothing: a change shows at the next drawing.
6. **Autocomplete providers.** Built 2026-10-10. pi stacks each `ctx.ui.addAutocompleteProvider(factory)` over its built-in provider (`factory(current)`, the last added outermost) and its editor asks the stack at a trigger: `/` at the start of a line, `@` and `#` at a token boundary, any of the stack's `triggerCharacters`, and Tab (`force: true`); while the list is open each keystroke asks again. A picked item goes through the stack's `applyCompletion`. In PI WEB:
   - The daemon keeps each session's stack. Its base stands for pi's built-in provider, whose completions PI WEB draws in the browser (commands, files, models): it suggests nothing and applies an item the way pi's base does for a plain token (the prefix before the cursor replaced by the item's value). The status's standing extension UI carries `completion: { triggerCharacters }` while a stack exists; the stack ends with the session's extensions, as every standing value does.
   - `POST /sessions/:id/extension-completions { cwd, text, cursor, force }` asks the stack (`getSuggestions` over the text's lines, a signal aborted by the next ask for that session or after 2 s) and answers `{ prefix, items: [{ value, label, description? }] }`, bounded (50 items, 200 characters a field; an item whose value is longer is left out, since cutting it would change what is inserted), or no items. A session without a running runtime has no stack and suggests nothing; asking never starts one. `POST /sessions/:id/extension-completions/apply { cwd, text, cursor, item, prefix }` answers the stack's `applyCompletion` as `{ text, cursor }`; without a stack, or when the stack's apply throws, the base's.
   - The composer of a session with a stack asks the daemon first wherever pi's editor would (its own triggers and the stack's characters at a token boundary); items the stack answers are the list, else the composer's own completions are, as pi falls back to its built-in provider. Picking an extension item applies it through the daemon against the text it was suggested for; a draft changed meanwhile keeps the reader's typing, and a failed apply says so. A failed or slow ask leaves the composer's own completions. A newer ask, from any browser, aborts the older one's signal.
   - Tab is the composer's own key today (focus); forcing a completion with Tab is not carried over.
7. **Tools expanded, and `setTheme` answering plainly.** Built 2026-10-10. pi's `setToolsExpanded(expanded)` is its Ctrl+O: every tool row and every custom row an extension draws is redrawn expanded or collapsed, and `getToolsExpanded` answers it. In PI WEB:
   - The session's standing extension UI keeps the value and carries `toolsExpanded: true` while it holds; `getToolsExpanded` answers it, and it ends with the session's extensions, as every standing value does.
   - The session's tool cards open their output while it holds, as an error's card does, and fold back when it is cleared.
   - What the extensions draw from then on (tool call and result lines, custom rows) gets `expanded` as pi gives it. Rows the page has already read keep the drawing they were read with until the page reads them again; the card's own fold follows at once.
   - `setTheme` answers `{ success: false }` with the reason: PI WEB draws with its own themes, chosen in its Settings. pi's headless default said only "UI not available". `getAllThemes` and `getTheme` keep pi's headless answers (none).
